# Safari 复制修复（集成进本项目）

在 Safari 里让复制结果与**网页上看到的文字**一致,覆盖两类干扰:

1. **字体混淆** —— DOM 里的字符与字体渲染出的字形不一致(例如 DOM 是「天地玄黄」,显示的是「人工智能」)
2. **复制劫持** —— 网页在 copy 事件里 `preventDefault` 或用 `clipboardData.setData` 覆盖内容

**不使用 Safari 扩展、不需要付费开发者账号、不轮询剪贴板、不装键盘监听、不上传任何内容。**

---

## 架构

```
Electron 主进程
├── safari-repair/bridge.js        Apple Events 桥(执行页面 JS、注入、读状态)
├── safari-repair/engine.js        字形还原(Node 侧:解析字体文件 + 与参考库比对)
├── safari-repair/coordinator.js   注入调度(前台判定 / 幂等注入 / 映射下发)
└── safari-repair/index.js         模块入口 + IPC 注册

网页内(注入的 page-guard.js,11KB)
├── selectionchange → 按字体作用域分组,收集「用了哪个字体 + 哪些字符 + 字体文件」
├── copy 捕获(window 捕获阶段)→ 查映射表 → setData + preventDefault
└── stopImmediatePropagation + stopPropagation → 压过网页的劫持
```

### 字形还原:为什么是「解析字体文件」而不是「页面渲染位图」

页面侧曾用 canvas 渲染字形、回传位图给主进程比对。**这条路走不通**,实测数据:

| 方案 | 与参考库的距离 | 判定结果 |
| --- | --- | --- |
| 页面 canvas 渲染 → 主进程比对 | 相似度 0.87~0.97,margin 低至 0.005 | 「专」被判成「令」,错字 |
| 解析字体文件 → 主进程用同一套栅格化器比对 | 距离 0.001~0.043,margin 0.03~0.19 | 27/27 全对 |

原因:**canvas 的字形栅格化与参考库的栅格化器不是同一套**(抗锯齿/合成方式不同),
距离一旦拉大,最近邻就分不出「专」和「令」。所以现在:

- 页面只做两件事:① 按字体作用域分组上报「这段用了哪个字体、哪些字符」;② 把该作用域对应的
  `@font-face` 字体文件(常见是 `data:` 内嵌的 base64)一并上报。**页面不做任何字形识别**。
- 主进程用 opentype.js 解析字体,用**与参考库完全相同**的栅格化器(48×48、4bit 量化)把字形转成位图,
  再与 Noto Sans SC 参考库做最近邻匹配。
- 只有「字体确实把这个码位画成了别的字」(自身距离 ≥ 0.15)才替换;置信度不足就**不改**,
  保留用户原始复制内容。

参考库用 48×48 栅格:32×32 时「国」这类方框字分不出来(27 中只中 25),
48×48 才 27/27 全中。

### 参考库:只带一套黑体(48×48)

实测:换参考字体会直接改变结论 —— Noto Sans SC 平均距离 **0.031**(27/27 全中),
Noto Serif SC 0.118(错 4 个)。**距离小 = 参考库字型越接近底稿。**

字体文件的 `name` 表记着底稿字族(实测 `Source Han Sans CN Normal` = 思源黑体),
而思源黑体与 **Noto Sans SC 是同一字型** —— 所以只带 Noto Sans SC 一套就够,
包更小、命中更稳(合成字体对照实验:用黑体库 131/132、0 错;换宋体库掉到 100/132、26 个字进"不确定")。

引擎仍会读 `name` 表把底稿字族记进日志,便于日后换底稿时判断要不要换参考库。

参考库 48×48 栅格:32×32 时「国」这类方框字分不出来(27 中只中 25),48×48 才 27/27。

### 映射按字体建,不按选区建(重要)

引擎把**整个字体**的码位对照表一次性下发,而不是只下发"当前选区里出现过的字"。

原因:按选区建的话,用户后来扩大选区,新出现的密文字就不在映射里 → 复制出来还是乱码
(真实缺陷:5 道题只还原了第 1 题)。`safari-repair/test/loop.cjs` 的第二阶段专门守这个点。

### 规模:字体里所有可能用到的字全部映射

引擎把**整个字体**的码位对照表一次解完并整份下发 —— 不是"这次选区里出现过的字"。

性能上用 `safari-repair/fast-matcher.js`(精确哈希快路径 + 部分选择的快速最近邻):

| 字体规模 | 耗时 | 覆盖率 | 正确率 |
| --- | --- | --- | --- |
| 27 字(真实站点当前) | 120ms | 27/27 | 27/27 |
| 1000 字 | 169ms | 1000/1000 | 1000/1000 |
| 3000 字 | 435ms | 3000/3000 | 3000/3000 |

断言在 `node safari-repair/test/stress-font.cjs`。

### 保守闸门

margin / 相似度 / 自身距离 任一不足 → **该字不替换**,保持原样。
宁可留一个错字,也绝不写出错字。合成字体那 1 个未解出的字就是被闸门挡下的。

### 字体内容指纹

作用域 key 带字体内容哈希(`…|font-cxsecret#<hash>`):站点换字体(族名不变、字形全变)时
→ 新作用域 → 重新映射,不会拿旧字体的映射套新字体。

### 关键机制(都是本机实测踩出来的)

| 机制 | 说明 |
| --- | --- |
| **Apple Events 注入** | `do JavaScript` 把守卫脚本注入当前标签页;JS 走临时文件传递,内容一律 ASCII 化(本机区域设置是 GBK,直接传中文会乱码) |
| **window 捕获阶段 + stopImmediatePropagation + stopPropagation** | WebKit 的 `clipboardData` **不是** `DataTransfer` 实例,patch 原型对它无效;只能靠事件传播控制阻断网页劫持 |
| **internalCall 标志** | 护栏必须区分"自己调用"和"网页调用",否则我们自己的 `preventDefault` 会被自己拦下,事件从未取消,浏览器提交原始选区 |
| **页面不做识别** | 页面只上报「用了哪个字体 + 哪些字符 + 字体文件」;字形库与匹配**全在主进程**;映射异步下发到页面缓存,复制时**同步**查表改写,无竞态 |
| **执行环境判定** | 判断"守卫是否还在"靠哨兵(`window.__copyRepairGuard`),**不能只看 URL** —— 同 URL 刷新时 URL 不变但 JS 环境已重建 |
| **前台才动作** | Safari 不在前台时不做任何注入与匹配,避免无意义的系统调用 |

## 开关与状态

主界面第一个 Step 顶部有「Safari 复制修复」开关(默认关闭,不影响既有用户)。
状态经 `window.cnc.safariRepair` 暴露:

```js
cnc.safariRepair.getStatus()      // { enabled, injected, safariRunning, mappings, unresolved, ... }
cnc.safariRepair.setEnabled(true)  // 立即启用/停用调度
cnc.safariRepair.checkNow()        // 手动跑一轮检查
```

启用状态持久化在 `userData/settings.json` 的 `safariRepairEnabled` 字段。

## 首次使用需要的一次性授权

Safari 默认禁止外部进程执行页面 JavaScript,需要用户手动打开:

**Safari → 设置 → 高级 → 勾选「显示网页开发者功能」**（打开开发菜单）
→ **开发 → 允许来自 Apple Events 的 JavaScript**

本项目不擅自修改系统隐私设置;未授权时状态里 `lastError` 会记录失败原因,界面提示用户。

## 已知限制

- 守卫接管复制时会 `stopPropagation`,网页因此**收不到 copy 事件**(仅在存在可信字体映射时接管)
- 字体映射未就绪时,第一次复制仍会是原始内容(预计算需要一轮)
- 参考字形库覆盖 **GBK 全集 21517 字** + 常用符号;库外字符(如连 GBK 都没有的生僻字)不还原、不猜测
- 跨风格(衬线 ↔ 无衬线)还原率明显低于同风格,未命中的字符保持原样
- 换题后**约 1 秒**的窗口期内复制,拿到的仍是原始密文(映射还没算完)
- Safari 窗口里的页面 JS 环境每次导航都会重建,需要重新注入(由调度器自动完成)

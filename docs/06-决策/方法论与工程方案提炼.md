# 从任务书提炼：工作方式 + 工程方案

> 来源：外部提供的《macOS Safari 无扩展复制修复工具》任务书。
> 本文不照抄任务书，而是提炼它**教的方法**与**它设计的方案**，并对照本仓库现状给出落地改法。

---

## 一、它教的工作方式（可迁移到任何工程任务）

1. **先验证"决定架构是否成立"的那一个机制**，再动手做 UI 和其余部分。
   → 不是"先搭框架再验证"，而是"先用最小实验把承重墙验掉"。
2. **可证伪的实验设计**：每个实验列出要验证的具体条目（"App 能发 Apple Events""同 URL 刷新后恢复""同一页面多次检测不产生重复监听器"），而不是笼统目标。
3. **禁止用模拟成功代替真机测试**；要求"不能只测试从 Xcode 或 Terminal 启动的情况"——要测真实用户的首次安装路径。
4. **结论必须分级**：官方 API 明确保证 / 本机已实测 / 仅社区经验 / 尚未验证的假设。四类分开写，关键依据附原始文档链接。
5. **如实给出失败记录**，并区分"可解决 / 部分解决 / 技术上无法解决"，不允许用"跑通了"掩盖边界。
6. **遇到根本性阻断，先保留证据、报问题与最小解决代价，不擅自改路线**。
7. **不靠堆规则、抽象层和复杂架构掩盖未解决的核心问题**（第 4 条执行原则直译）。
8. **两类问题不许混为一谈**：复制事件篡改 ≠ 字体混淆还原，必须分别实现、分别验证。
9. **测试矩阵逐项报告预期/实际/是否成功**，并覆盖"已被监听器抢先""动态注册监听器""iframe/Shadow DOM"等刁钻场景。
10. **最终验收标准是用户真的能用**，不是"脚本执行成功"——交付物定义直接写死为"用户安装、后台运行、像往常一样复制"。
11. **规模指标化**：≥50 次刷新/切换/导航组合，测注入成功率、恢复延迟、空窗期，而不是报告一次成功。
12. **不为了达标偷偷放宽安全与隐私约束**。

**对照本仓库**：①②③⑤⑥⑩⑫ 我已在做（Phase 1 全部结论都带证据与出处）；
**尚缺**的是 ⑪（规模指标：50 次组合测试、空窗期测量）、以及 ④ 里对"用户真实首次安装路径"的验证（当前只测了开发路径）。

## 二、它的工程方案

### 2.1 总体形态

```
原生 macOS App（Swift + AppKit，菜单栏常驻，无 Dock 图标）
  ├─ Background App：状态、授权提示、登录自启、调度、退出清理
  ├─ Safari Automation Bridge：Apple Events 控 Safari（NSAppleScript / OSAKit）
  ├─ Injection Coordinator：何时、向哪个标签注入、幂等与恢复
  └─ 页面内 Copy Repair Engine：copy 拦截 + 字体还原（跑在网页上下文里）
```

### 2.2 关键机制（决定了它为什么能"无感"）

| 机制 | 作用 | 关键约束 |
| --- | --- | --- |
| Apple Events `do JavaScript` | App 把代码注入网页并取回结果 | 需用户开启「允许来自 Apple Events 的 JavaScript」 |
| 页面内 copy 捕获 | 在页面自己的上下文里抢在网页之前处理 copy | 必须在**窗口捕获阶段**；后注册的监听器不一定能阻止先注册的 → 需实测 |
| `stopImmediatePropagation` / `preventDefault` / `clipboardData.setData` | 组合拳决定最终写入内容 | 与我已实测的 Chromium 提交机制一致：**必须 preventDefault 才会提交改写** |
| 注入幂等哨兵 | 页面 JS 环境重建后重新注入，重复注入不叠加监听器 | **检测 URL 变化不够**：同 URL 刷新 URL 不变，必须验证"执行环境是否还存在" |
| 调度：NSWorkspace 激活通知 + 低频可取消检查 | Safari 不在前台就停；不持续产生无意义 Apple Events | 禁止用剪贴板轮询当触发源 |
| 退避机制 | Safari 繁忙/拒绝脚本时退避 | |

### 2.3 约束清单（它明确划的红线）

- 不用 Safari 扩展（含第三方脚本扩展）
- 不要付费开发者账号；必须支持无证书构建与分发
- 不关 SIP / Gatekeeper / 浏览器安全防护
- 不用键盘记录器 / 全局按键监听 / 输入事件劫持
- 不在后台持续读 NSPasteboard、不监控剪贴板历史
- 不记录/存储/上传浏览内容、复制内容、网址
- 不用远程 OCR、云端 AI、第三方内容分析
- **不要求用户每次复制时点按钮/跑快捷指令/执行脚本** ← 这条直接否掉了我原来的"热键工具"定位
- 不用 Safari 私有 API、二进制注入、绕过系统安全机制

### 2.4 它对"字体混淆"的技术要求

- 必须单独实现/验证，不能用"复制事件修复"顶替
- 研究链路：getComputedStyle → CSS FontFace 与字体资源定位 → OpenType/WOFF/WOFF2 字形映射 → 本地字形轮廓匹配 → 必要时本地字形识别
- **不能认为 getSelection().toString() 就是用户看到的文字**
- **不能只替换私用区字符就宣称解决**
- 字体不可访问/识别不可靠/有歧义时**不得猜测输出**，要保留原文或明确标记不支持
- 允许先只支持一类混淆字体做闭环，但架构要能扩展新的还原方法

### 2.5 交付与分级

要：完整源码、可运行 .app、无证书构建脚本、首次安装授权说明、测试网页与测试字体、自动化测试说明、测试结果与失败记录、架构文档、已知局限、卸载清理方案。

## 三、它与我现有方案的差异（以及我要怎么改）

| 维度 | 我现在做的 | 任务书的方案 | 我的落地改法 |
| --- | --- | --- | --- |
| 交付形态 | Node 脚本 + 快捷键 App（**每次复制按一下键**） | 菜单栏常驻原生 App，**零额外操作** | **改**：做原生 App，注入时机交给 App 的调度器 |
| 复制拦截位置 | Chromium：扩展主世界护栏；Safari：事后改剪贴板 | **页面内**（窗口捕获阶段）抢在网页之前 | **改**：拦截逻辑全部下沉到页面内，Safari 不再依赖"事后修正" |
| 字体还原位置 | Chromium：后台匹配；Safari：App 侧(Node)匹配 | 页面内做还原 | **改**：页面内渲染位图 + App 侧匹配 + 映射表异步下发回页面缓存 → 复制时同步查表 |
| 调度 | 无（用户触发） | NSWorkspace 激活通知 + 低频检查 + 幂等注入 | **改**：新增注入协调器 |
| 隐私 | 已满足 | 已满足 | 保持；不引入剪贴板轮询、不引入键盘监听 |
| 匹配引擎 | TypeScript（已验证：同风格 100%、跨风格门限内精度 100%） | 要求本地字形轮廓匹配 | **保留**：不重写，把已验证的 TS 引擎打包成 IIFE 交给 App 内嵌 JS 引擎执行 |

### 关键设计：字形库 4MB 怎么进页面而不拖慢它

页面不能同步向 App 提问（页面→App 无同步通道），所以不能"复制时才现算"。采用两段式：

```
用户选中文字
   ↓ selectionchange（页面内）
页面渲染该字体的字形位图 → 暂存到 window.__crPending
   ↓ App 低频轮询取回（异步，预计算阶段不敏感）
App 侧匹配（字形库在 App 内存里，不进页面）→ 得到 char→char 映射
   ↓ App 写回页面
页面缓存映射表到 window.__crMapping
   ↓ 用户按 Cmd+C（同步）
页面 copy 捕获 → 同步查 window.__crMapping → setData + preventDefault
   → 浏览器提交修复后的文本（无竞态）
```

空窗期 = 「用户选中 → 映射下发」这一段；命中缓存时为空窗 0。

## 四、本仓库随之要改的清单

- [ ] `apps/macos-app/`：Swift 菜单栏 App（状态、授权引导、登录自启、注入协调器、诊断）
- [ ] 页面内注入脚本：幂等哨兵 + 窗口捕获 copy 拦截 + 位图渲染 + 映射缓存
- [ ] 匹配引擎打包成 IIFE，交给 App 内嵌执行（字形库留在 App 侧，不进网页）
- [ ] 复制场景测试矩阵扩到 10 项（含 window/document 捕获、冒泡、stopImmediatePropagation、动态注册、input/textarea、contenteditable、iframe、Shadow DOM）
- [ ] 规模测试：≥50 次刷新/切换/导航组合，测注入成功率、恢复延迟、空窗期
- [ ] 字体混淆：保留已验证的 TS 引擎，额外补"未知字形/相似字形/标点/数字"用例
- [ ] 无证书构建脚本 + 首次安装与授权说明（Gatekeeper 正常开启下的首次打开流程）
- [ ] 结论分级文档：官方保证 / 本机实测 / 社区经验 / 未验证假设

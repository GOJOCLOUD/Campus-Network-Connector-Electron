# ADR-0024:浏览器没了不许「反反复复拉起」—— 六个坑一起堵上,用户自己关掉的窗口不自动再弹

- 状态:**已定**
- 日期:2026-10-27
- 用户原话(2026-10-27 18:01):
  > 「只要我打开了，他就反反复复拉起浏览器，而且拉起浏览器一直都是失败，根本就没有一个窗口，起来的浏览器根本就不能用」
- 相关:ADR-0022//ADR-0032(先找再起)、ADR-0020//ADR-0030(自起浏览器 + CDP 注入守卫)
- 谱系:Tauri 侧是**同一条决策**的 ADR-0034,两边行为一致。

---

## 一、现象

用户打开软件 ⇒ 浏览器**一个接一个地被拉起**;用户看到的是「没有窗口」,
起来的那几个「根本就不能用」。

## 二、真机取证(2026-10-27,怎么查出来的)

不是猜的,是量出来的:

1. **把 App 的 stdout 逐行加时间戳**,同时**每秒**记一次 Edge 的进程数与窗口标题
   ⇒ 看到「启动 Edge(端口 61655)→ 浏览器已就绪」**连着三次**,每次都是**新端口**
   (61655 → 58658 → 59831)⇒ 说明每一次都是「**新起了一个**」,不是「连回同一个」。
2. **对照实验**:用**完全相同**的参数手动起 Edge,连做 6 轮
   ⇒ **6/6 全部在 1 秒内把调试端口开起来**,窗口也正常。
   ⇒ **「起浏览器」这件事本身没问题** ⇒ 问题在「起了之后又起」。
3. **关窗实验**:App 正常运行 ⇒ **把 Edge 窗口关掉** ⇒
   ⇒ 约 20 秒后 App **又拉起一个新的 Edge**(端口从 60951 起),还带一个
   「还原页面」气泡、之前开的标签页**全丢**。
   ⇒ **这就是「反反复复拉起浏览器」**。
4. Edge 自己的退出记录:本机**没有**崩溃报告、事件日志也干净
   ⇒ 它是**干净退出**的(不是崩的)。

## 三、六个坑(逐条对应根因,逐条对应下面的改动)

| # | 坑 | 后果 |
| --- | --- | --- |
| ① | `ensure()` **没有互斥**:主轮询(300ms)/快轮询/IPC 三条路各自调它 | 谁先发现「浏览器没了」谁就起一个 ⇒ **起好几个** |
| ② | 连「**已经在跑的**浏览器」也要**等 5 秒**才放弃 | 每个候选端口白等 5 秒 ⇒ 「半分钟才动一下」 |
| ③ | `findRunningPorts()` 用 `execFileSync`(**同步**) | **把 Electron 主线程卡住最多 15 秒** ⇒ 界面不刷新、CDP 事件不处理、⌃D 的低级键盘钩子拿不到回调(Windows 会把超时的钩子摘掉) |
| ④ | 起不来就**无限重试** | 一个接一个地弹 |
| ⑤ | Edge 自己的 stdout/stderr 被 `stdio:'ignore'` **丢掉了** | 出了事日志里**一个字都没有** ⇒ 查了半天 |
| ⑥ | 分不清「**用户关掉了窗口**」和「**崩了**」 | 用户关的窗口也被自动弹回来 ⇒ 越关越弹 |

## 四、决策

1. **`ensure()` 加单飞锁** —— 并发的调用共享**同一次**尝试。
2. **`tryAttach()` 快速失败** —— 等端口从 5 秒降到 0.8 秒(端口没开就是没开)。
3. **扫进程改异步** —— 不再卡主线程。
4. **失败有上限** —— 连着起不来 3 次就**停下来**,并把原因报给界面,不再无限重试。
5. **留住浏览器自己的输出** —— 落到 profile 目录的 `browser-stdout.log` /
   `browser-stderr.log`,以后出事能直接看。
6. **记住退出码** —— 我们起的那个浏览器进程自己退出时:
   - 退出码 **0** = **用户关掉了窗口**(干净退出);
   - 退出码 **非 0** = 崩了 / 被强杀(本机实测 `Stop-Process` 拿到 4294967295)。
   ⇒ 区分得出来,才能分别对待。
7. **用户自己关掉的窗口 ⇒ 不再自动弹一个**;界面改成显示
   「浏览器已关闭 —— 本软件不会自动再弹一个」+ 一个 **「重新打开浏览器」** 按钮。
   **崩溃/被强杀仍然自动恢复**(那不是「用户关的」)。

⚠️ 第 7 条是**产品口径**(界面文案与行为都变了),实现上是一个开关
(`coordinator.autoReopen` / `CoordState.auto_reopen`),改回「关掉也自动重开」
只要把那一个值改回去。

## 六之二、2026-10-27 真机复验又抓到一个 **race**(装上 v5 之后)

v5 装上、真机复验「关掉那个 Edge 窗口」时,日志是这样的:

```
[10:48:25.824] [out] 浏览器进程退出：code=0 signal=无（用户关掉了窗口）   ← 认出来了
[10:48:26.820]   · edge进程=0 窗口=[]
[10:48:27.925] [out] 启动 Edge：…（端口 53114）                            ← **还是弹了一个**
```

**「用户关的」明明已经认出来了,却还是又弹了一个。**

### 根因:判定放在**错的位置**

`tick()` 每 300ms 一轮。浏览器的「进程退出事件」与 WebSocket 的「连接断开」
几乎同时到达,但**处理顺序不保证**:

1. 某一轮 tick 在退出事件**还没被处理**时就开跑了
   ⇒ 它看到 `closedByUser() == false` ⇒ 放行;
2. 它接着走 `ensure()` → 连不上 → **起新的**;
3. 退出事件这时才被处理 —— 已经晚了,浏览器已经弹出来了。

⇒ **判定必须放在「真正起浏览器之前」**,而不是只在 tick 开头看一次。
走到 `launch()` 那一行时,前面的 tryAttach + 扫进程已经花掉约 2 秒
⇒ 退出事件**一定**已经被处理了。

### 改法

- `ManagedBrowser` 多一个 `autoReopen`(产品口径,由协调器下发);
- `ensureOnce()` 在 `launch()` **之前**再判一次:
  「这个浏览器是我们起的、它刚刚干净地退了(退出码 0)、而口径是「不自动重开」」
  ⇒ 抛一个带标记的错误 `BROWSER_CLOSED_BY_USER`;
- 协调器把那个错误**认出来**（**不是「失败」**,是「用户关的」）
  ⇒ 状态置 `browserClosedByUser`,界面显示「重新打开浏览器」按钮。

### 门禁

`verify-browser-loop-guard.cjs` 加一关
「真跑:用户关掉浏览器 ⇒ 不该再弹一个」:真起一个 Edge、真关掉、真跑五轮 tick
⇒ 断言**端口没变**（没有起新的）+ **状态如实上报**。

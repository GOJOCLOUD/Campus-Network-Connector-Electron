# Campus Network Connector — 项目记忆

## 项目性质
Electron + React 桌面应用，模拟鼠标点击和键盘输入，用于校园网自动登录等场景。

## 架构演变

### ❌ 旧架构（已废弃）
```
Electron → Python FastAPI (port 51888) → automation_worker.py 子进程
```
问题：macOS 权限链太长，每个环节都要授权 Accessibility，子进程经常拿不到权限导致静默失败。

### ✅ 当前架构
```
Electron 主进程 → Native N-API addon → 系统 API（CoreGraphics / Win32）
```
单进程，一次授权即可。

## 平台支持

**两个平台各打各的包,分支分开,不共用打包入口。**

> 详细边界、环境分工、并行 Agent 协作约定 → **[两条发布线.md](两条发布线.md)**(接手前必读)

| 平台 | 分支 | 安装包类型 | 原生模块 | 界面步骤 |
|------|------|-----------|---------|---------|
| macOS (arm64) | `mac` | .app(zip) | `mac-coregraphics` | 激活 → 默认执行 → 模拟点击 → 键盘输入 |
| Windows (x64) | `win` | exe (NSIS) | `win-input` | 激活 → 默认执行 |

| 平台 | 构建状态 |
|------|---------|
| macOS (arm64) | ✅ CI 通过,已发布 |
| Windows (x64) | ✅ CI 通过,已发布 |

- 各分支各有一份 `package.json` 的打包配置 + 各自的 GitHub Actions workflow
  (`mac` → `build-desktop.yml`,`win` → `build-windows.yml`)。
- 界面的平台差异靠**运行时平台判断**(`window.cnc.platform`)裁剪,两条线目前共用同一份源码:
  Windows 上不渲染「模拟点击(录制)」和「键盘输入(快捷输入)」,录制文件的
  挑选/重命名/删除保留在「默认执行」那一步的「管理」入口。
- Safari 复制修复走 Apple Events,**只有 macOS 有** → 功能注册表 `src/features/index.js`
  用 `platforms` 字段过滤,不在白名单里的功能连 require 都不做。
- `win` 分支**从建仓库第一天起就是 Windows 线**,不是后来重建的(它的第一个提交
  就是「模拟输入 · Electron 版(Windows 线)」)。
  ⚠️ 历史上真正被删掉的是**另一个更早的 `win` 分支**(代码停在 2026-07 之前,
  原生模块塞在 asar 里 → 装上就崩)—— 别把这两件事搞混。

## 两条线共同踩过的坑:原生模块必须在 asar 之外

`mac-coregraphics` / `win-input` 是原生模块(.node),Electron **不能从 asar 里 dlopen**,
必须落在 `app.asar.unpacked/`。违反这条的后果:

- macOS:整个 App 能起来,但模拟输入/输入源/录制回放**整组功能全废**(ADR-0003)。
- Windows(旧 `win` 分支):更糟 —— `main.js` **顶层无条件 require** 原生模块,
  加载失败直接把主进程带崩,**App 根本起不来**,用户看到的就是"用不了"。

因此两边都遵守三条:

1. `package.json` 显式声明 `asarUnpack`(mac:`mac-coregraphics/**`,win:`win-input/**`),
   不依赖 electron-builder 版本的自动行为;
2. 原生模块按平台加载 + **失败要响**(try/catch + `native:getStatus` + 界面红条),
   不做"安静的失败";
3. 打包后必须跑产物自检,把"原生模块已解包且能加载"变成硬门禁
   (`verify-package.cjs` / `verify-package-win.cjs`,CI 里都会跑)。

## 文件结构（关键文件）

```
├── main.js                          # Electron 主进程（IPC + 播放逻辑）
├── preload.js                       # 上下文桥接
├── package.json                     # 构建脚本、electron-builder 配置（本分支只管本平台）
├── src/                             # React 前端（Vite + Tailwind）
│   ├── App.jsx                      #   步骤编排（按平台裁剪：Windows 只有前两步）
│   ├── panels/                      #   各步骤面板（纯展示，动作交给 App）
│   └── features/index.js            #   功能注册表（platforms 字段做平台过滤）
├── mac-coregraphics/                # macOS 原生插件（本分支）
│   ├── src/main.mm                  #   CoreGraphics / Carbon API 调用
│   ├── index.js                     #   加载器
│   └── binding.gyp                  #   node-gyp 配置（参考用，实际用 clang++ 编译）
├── electron/
│   └── after-pack.cjs               #   打包后签名（优先钥匙串真证书，签不了才 ad-hoc）
├── backend/                         # 点击数据 JSON 文件存储目录
├── .github/workflows/
│   └── build-desktop.yml            #   macOS CI（mac 分支触发）
└── .gitignore
```

> Windows 线（`win` 分支）里对应的是 `win-input/`（Win32 插件）和
> `build-windows.yml`（Windows CI）。

## 待办 / 已知问题

- `after-pack.cjs` 打包后签名(macOS;非 mac 平台自动跳过):
  ad-hoc **整包**签名,目的只有一个 —— **签名必须有效**
  (无效签名会被 Gatekeeper 判成「应用已损坏」,比「无法验证开发者」更难绕过)。
  **不追真证书**:为「让『辅助功能』授权跨版本留住」而挑固定证书的那套已废除
  (2026-10-24 用户口径:重新安装要重新授权是正常代价)。
- Windows 侧 `win-input` 的录制能力（`SetWindowsHookEx`）**界面未启用**，
  业务上不需要；`LoadKeyboardLayout` 那套输入法切换在现代 IME 上兼容性存疑
- Windows CI 固定用 `windows-2022`：node-gyp 在 VS2026（windows-latest 现在指向
  windows-2025-vs2026）上找不到匹配工具链会构建失败
- 两条线目前靠人工同步：`mac` 的改动要合到 `win` 分支时，
  `package.json` / `preload.js` / `win-input` 这几处会有冲突，属预期内

## 接下来怎么走

1. **改动会推 GitHub**:`mac` / `win` 各自推各自 —— CI 靠 push 触发,产物作为
   release 附件发布;桌面交付包另走本机脚本(见上)。
   (2026-10-21 那条「不再往 GitHub 推送、`git push` 一律不做」的口径**已作废** ——
   CI 本来就靠 push 才能触发。)
2. **两条线不互相回流**:同一个产品的另一个正式版本(Tauri 版)在独立仓库,
   **同等优先**(不是"新的取代旧的")。改动要搬就**显式搬**,并在提交说明里写清搬的是什么。
   协作规矩(只提交自己动过的文件、别把别人在途改动卷进来、两条线的冲突不用解)
   写在 [两条发布线.md](两条发布线.md)。
3. **同一个功能在两个平台上的行为必须一致**(2026-10-24 用户定):快捷键与触发规则、
   latch 语义、错误处理与提示、界面结构与文案、门禁 —— 都要对齐。
   但**实现方式与打包配置可以各自不同**;平台专属能力(辅助功能/输入源/Safari)
   按 ADR-0012 各做各的。**"行为一致"不等于"实现一样"。**
4. Windows 包没在真 Windows 机器上跑过,这不阻塞:CI 已经证明它能构建、
   原生模块能加载、包内容正确。真机验证等有空再说。

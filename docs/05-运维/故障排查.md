# 故障排查

## 「模拟输入/输入源/录制」按钮点了没反应

1. 看界面顶部有没有红色告警条(原生模块加载失败)
2. 命令行看日志:
   ```bash
   grep "\[native\]" /tmp/app.log     # 或从终端启动 App 直接看输出
   ```
3. 检查安装包:
   ```bash
   node tools/verify/verify-package.cjs "/Applications/模拟输入.app"
   ```
   看「原生模块已解包到 app.asar.unpacked」是否 ✅
4. 常见原因:**只换了 app.asar 没换 app.asar.unpacked**(见 ADR-0003)

## Safari 复制修复不生效

按顺序排查:

1. **功能开关是否开着**:界面「Safari 复制修复」= 开启;或看
   `~/Library/Application Support/xyw/settings.json` → `features["safari-repair"].enabled`
2. **App 是不是退出了**:关窗口不该退出(macOS 惯例)。看进程:`pgrep -fl 模拟输入`
3. **目标页有没有被接管**:页面上应有 `window.__copyRepairGuard`
4. **是不是没等到映射**:刚打开页面 1 秒内复制可能还没建好映射 → 等 2 秒再试
5. **自动诊断**:
   ```bash
   node tools/lab/real-page-run.cjs 19 1     # 手动驱动一轮,看日志
   node tools/lab/font-extract.cjs 19         # 把当前页的加密字体抠出来看底稿字族
   ```

## 换题之后复制出来还是密文(2026-10-23 修掉的真实故障)

**症状**:第一题能修好,换一题之后又变密文;有时连着几题都不行。

**根因**:iframe 桥的 frame 名单**过期**。真实目标页的题目在**第 4 层同源 iframe** 里,
而站点(SPA)是在**嵌套 frame 内部**换 iframe 的(换题、翻页、加载下一段)——
顶层那个 MutationObserver **看不见**嵌套里的变化 → 名单一旦过期:

- 映射被发到上一套 iframe(浏览器上已经变成 `about:blank` 的那些);
- **真正在显示题目的那层一份映射都收不到** → 那层复制出来还是密文
  (守卫日志是 `copy-no-mapping`)。

真机证据:bridge 名单里 **17** 个 frame,而当前页面树只有 **10** 个(8 个过期残留);
手动 `rescan()` + 分发一次 → 题目那层立刻拿到映射 → 复制出来是明文。

**修法**:`take()`(收集)与 `setMapping()`(分发)**开头都先 `scan()`**,
`scan()` 把当前树里没有的旧 frame 从名单里剔掉。

**回归测试**:

```bash
node --test tools/verify/verify-frame-bridge.cjs
```

它用纯 node 造一棵假 frame 树模拟"站点换掉 iframe",断言**新那层必须收到映射**;
同一个测试拿修复前的源码跑会红(3 个用例红 2 个)。已接进 CI 门禁(跑不过就不发包)。

## 复制出来的还是怪字,但界面显示正常

说明字体识别失败。查:

- 该作用域的字体是否可读(`@font-face` 在跨源样式表里就读不到 → 不还原)
- 识别置信度不够时会**故意不改** → 宁可留怪字

## 复制只修好一半(前半句明文、后半句密文)

这是 2026-10-21 修掉的真实故障(根因见 ADR-0005):查表要两样东西,
"这个字画成了哪个字"来自主进程的映射表(按字体整份下发,不会过时),
但"这个字属于哪个字体作用域"曾经是**采集缓存**——采集比复制慢一拍,
于是**刚选到、还没采集过的新密文字**查表落空 → 原样进剪贴板。
早先选过的字在缓存里 → 修好了(所以看起来"只修好一半")。

**现在复制时当场按当前选区解析作用域,不再依赖缓存。**
如果又出现同样现象,先确认页面里的守卫版本:

```bash
node tools/lab/diag-frames.cjs chaoxing        # 看每层 frame 的守卫状态与作用域
node tools/lab/diag-apply.cjs <tab> judge      # 逐字复算查表路径,看是谁落空
node tools/lab/verify-fastcopy.cjs --tab <tab> # 清空采集缓存后立刻复制,必须全还原
```

`verify-fastcopy.cjs` 是这个故障的**回归测试**:它清空采集缓存再复制,
旧守卫会红(剪贴板留原样密文),新守卫必须零残留。

## 打包后 App 起不来 / 功能全废

跑 `node tools/verify/verify-package.cjs`,逐项对照。

## 标签页序号对不上

Safari 的标签序号会变(关标签/重排)。**不要用固定序号**,用 URL 定位
(`tools/verify/verify-app-e2e.cjs` 里是按 URL 找的)。

## Windows 上快捷键没反应(2026-10-24 新增;2026-10-25 / 2026-10-27 两次改口径)

> ⚠️ **2026-10-27 起,Windows 线抢 ⌃D(主键)+ ⌃⇧D(容错别名),不抢 ⌃S**(ADR-0021)。
>
> - **⌃D(读剪贴板并键入)**:我们**要抢**它 —— 抢到手,别的软件就**收不到** Ctrl+D,
>   那个软件也就不会被自己的「收藏夹 / 退出」之类动作干掉
>   (用户口径:「干脆直接把系统的抢了,我的软件优先级最高」)。
>   ⚠️ **代价要知道**:⌃D 在 Edge/Chrome 是收藏夹、VS Code 是选中下一处、Excel 是向下填充
>   ⇒ **本软件开着的时候,别的软件里按 Ctrl+D 它们收不到**。这是抢全局键的固有代价。
>   ⚠️ 但注册是**系统级独占**的:别的软件先注册了同一个组合键 ⇒ 我们**抢不到**
>   ⇒ 按 ⌃D **不会触发我们**,而目标软件自己的 Ctrl+D **照常生效**
>   ⇒ **抢没抢到,界面上直接写着**：「键盘输入」页有一条**琥珀色提示**
>   「Ctrl+D 没抢到(这个组合键被别的软件先注册了):按它不会触发我们,
>   目标软件自己的 Ctrl+D 也会照常生效。」
>   —— **看到那条提示 = 没抢到**(不是软件坏了)。
> - **⌃⇧D 是容错别名**(同一个动作):系统的全局热键是**精确匹配**,
>   手上多带一个 Shift 时 ⌃D 不会触发 ⇒ 别名把那条路兜住。
> - **⌃S**:**仍然不抢**(Windows 上「默认执行」那一屏已经撤了,ADR-0016;
>   而且 Ctrl+S 在别的软件里是「保存」,抢过来会把人家的保存弄坏)。
>   ⇒ 「按 ⌃S 没反应」在 Windows 上是**预期行为**。
>
> 诊断里能一眼确认:
>
> ```js
> await window.cnc.getNativeStatus()
> // → { ok: true, platform: 'win32',
> //     shortcutCtrlS: false,          // ← ⌃S 按政策不注册
> //     shortcutCtrlD: true,           // ← ⌃D(主键)注册成功 = 抢到了
> //     shortcutCtrlShiftD: true,      // ← ⌃⇧D(容错别名)注册成功
> //     globalShortcutsEnabled: true,  // ← 全局键这条路是**开**着的
> //     shortcutPasteRegistered: true, // ← false = **没抢到**
> //     latchAvailable: true, latchArmed: true, controlWatcherRunning: true }
> ```
>
> 下面这几步是排查步骤 —— 2026-10-24 之前全局键是**关**的,现在**开**了,正好用得上。

Windows 线上现在注册的是 **⌃D**(读剪贴板并键入)+ **⌃⇧D**(容错别名);**⌃S 不注册**
(「默认执行」那一屏在 Windows 上已经撤了,ADR-0016;而且 Ctrl+S 是别的软件的「保存」)。

**按这个顺序查,别跳步** —— 每一步都对应 `native:getStatus` 里的一个字段:

### 第 1 步:热键**注册**成功没有

看启动日志里这一行:

```
[shortcut] Ctrl+D=true Ctrl+Shift+D(别名)=true latch=true
```

- `Ctrl+D=false` ⇒ **全局注册失败**。
  最常见的原因:**别的程序已经占用了这个组合键**(系统级独占,只有全拿/全没有两种结果)。
  ⇒ **界面上会出现琥珀色提示**「Ctrl+D 没抢到…」—— 看到它就说明是这个原因,
  不是软件坏了。启动日志里也会有一条同名 warn。
- `latch=false` ⇒ 见第 2 步。

### 第 2 步:Control 边沿观察器在不在跑

`native:getStatus` 里:

| 字段 | 含义 |
| --- | --- |
| `latchAvailable` | latch 可用吗(= 只读观察器起来了没有) |
| `controlWatcherRunning` | 观察器线程在不在跑 |
| `latchArmed` | 当前是不是武装的 |

- `latchAvailable=false` ⇒ **拿不到 Control 的按下/松开** ⇒ latch 不可用
  (按住 Ctrl 连按会**连着触发**;而「默认执行」是回放 ⇒ 一次误触就是一串乱点)。
  启动日志里会有一条 warn:`[shortcut] 拿不到 Control 按下/松开的只读观察 ⇒ latch 不可用`。
  多半是**原生模块没重新编译**(旧版本里没有 `watchControlKey`)——
  重新构建:`npm run build:win-native`。
- `latchAvailable=true` 但 `latchArmed=false` ⇒ latch 正**锁着**:
  上一次触发还没消费完,必须**松开 Control 再重新按住**才能再触发。

### 第 3 步:动作到底执行了没有

- **⌃S 没反应**:看有没有回放的日志(`[playback]` / `[trigger]`)。
  没有任何日志 ⇒ 压根没进 `triggerDefaultExecute` ⇒ 回第 1 步。
- **⌃D 没反应**:⌃D 做的是「读剪贴板 → 逐字键入」。
  - 剪贴板**是空** ⇒ 不动作(这是设计,不是故障);
  - 键入没出来 ⇒ 看 `[native] sendText 调用失败` 或
    `getLastTextSendDiagnostics` 的诊断(没有前台窗口 / 目标窗口权限更高都会失败);
  - ⚠️ Windows 上 ⌃D **不切输入源** —— `sendText` 直接送 Unicode
    (WM_CHAR / KEYEVENTF_UNICODE),所以"输入法不对"不是它造成的。
- **录制的点击里混进了点自己界面的那一下**:排除矩形由主进程按窗口位置算,
  窗口 move/resize 时刷新 ⇒ 正常不会。若仍出现,看主进程有没有报
  `[native] setExcludeRect 调用失败`。

### ⌃D 在**某个软件**里不管用,但别的软件里正常

**现象**(2026-10-27 真人反馈):**在微信里**按 ⌃D 是微信自己的动作,
我们的「读剪贴板并键入」不触发;在别的软件里按 ⌃D 一切正常。

**这和「没抢到」是两回事** —— 注册**是好的**,界面上也**没有**琥珀色提示。
根因:**两种「抢」不在同一层**。

| | 机制 | 优先级规则 | 能不能被绕过 |
| --- | --- | --- | --- |
| 我们的实现 | `RegisterHotKey`(系统全局热键) | **先注册先得** | 不能 |
| 微信这类软件 | **低级键盘钩子**(`WH_KEYBOARD_LL`) | **后装的钩子先被调用** | 能(钩子返回非 0 就把键吞掉) |

Windows 的输入顺序是:**低级钩子 → 系统热键 → 目标窗口**。
微信的钩子在**系统热键之前**就把 Ctrl+D 处理掉了(多半还吞掉)
⇒ 我们**根本收不到 `WM_HOTKEY`** ⇒ 日志里也不会出现「⌃D 直输」那一行。

**当场确认是不是这种情况**(2026-10-27 在真机上做过):

1. 启动日志里 `[shortcut] Ctrl+D=true` ⇒ **系统热键注册是好的**,不是被抢占;
2. 用一个自己的进程调 `RegisterHotKey(Ctrl+D)`:
   - 失败(错误码 **1409** `ERROR_HOTKEY_ALREADY_REGISTERED`)⇒ 这个组合键
     **系统里有人占着**(实测:把我们自己退出后再调就拿到了 ⇒ 占用者是我们自己);
   - ⇒ 微信**没有**用系统热键占这个键 ⇒ 它走的是**钩子**那条路。

**已经改好了(2026-10-27)**:我们自己也装了一个**低级键盘钩子**
(`WH_KEYBOARD_LL`),看到 ⌃D 就**吞掉它** ⇒ 微信收不到、系统热键也收不到
⇒ 只有我们响应(详见 ADR-0023)。

⚠️ 但**不是绝对保证**:Windows 的规则是**后安装的钩子先被调用**
⇒ 本软件**后启动**就赢;对方后启动就对方赢。

**怎么看钩子装上了没有**:`native:getStatus` 的 `shortcutHookCtrlD` = true 就是装上了。

没装上时**如实降级**:还有系统热键那一路能用,只是压不过用钩子的软件。

## Windows 上「把密文还原成明文」不生效(2026-10-26 起形态变了)

Windows 线现在**不用扩展**了:桌面程序**自己起一个 Edge**,用 CDP 把页面守卫注进去
(见 ADR-0020)。所以排查顺序也跟着变了 —— **先确认用户是不是在那个窗口里用**。

### 先分清:两条线各自谁在干活

| 平台 | 谁在干活 | 界面上的形态 |
| --- | --- | --- |
| macOS | **桌面程序**(Apple Events 驱动 Safari) | 一个**开关**「Safari 复制修复」 |
| Windows | **桌面程序自己起的 Edge**(CDP 注入守卫) | 一个**开关**「浏览器复制修复」 |

⇒ 两条线界面上的开关位置与长相**完全相同**(最后一页最上面)。

### 排查顺序

1. **开关拨了吗** —— 最后一页最上面「浏览器复制修复」,点「开启」。
   状态文字应是「**已接管**」;如果停在「已开启」,下面会有**失败原因**那行。
2. **在不在「那个窗口」里用** —— 程序会打开**一个自己的 Edge 窗口**,
   守卫只装在**那个窗口**里。用户在**自己平时那个**浏览器里复制 ⇒ 永远是密文。
   这是最容易踩的一条,界面上也写了提示。
3. **浏览器开着吗** —— 关掉那个窗口没关系,程序会重新打开;
   但如果程序自己起不来,开关下面会写失败原因。
4. **登录了吗** —— 首次要在那个窗口里**扫码登录**一次超星。
   没登录 ⇒ 页面打不开 ⇒ 什么也复制不到。
5. **选区是空的吗** —— 页面若用 `user-select:none`,连程序化选区都取不到文本,
   守卫就**无字可改**(日志里记 `copy-no-mapping`)。这一条**尚未在真超星上验过**。
6. **开发者:跑端到端门禁** —— 一条命令把整条链路走一遍:
   ```bash
   npm run build:vendor
   node --test tools/verify/verify-cdp-copy-repair.cjs
   ```
   它真起一个 Edge、注入、真字形识别、下发、合成 Ctrl+C,
   并断言**系统剪贴板**里是明文。

### 桌面程序这边还有什么是坏的

| 现象 | 看哪儿 |
| --- | --- |
| 界面提示「Ctrl+D 没抢到」 | 快捷键被别的软件先注册了 ⇒ **快捷键**这条路不通,但**浏览器修复**那条路是独立的,不受影响 |
| ⌃D 在**微信**里不管用(别的软件里正常) | 微信用**低级键盘钩子**抢走了键(它在系统热键**之前**)⇒ 我们收不到热键。启动日志 `Ctrl+D=true` 说明注册是好的 ⇒ 这不是「没抢到」,是**层级**问题 |
| Edge 每隔一会儿自己弹出一个空白标签页、复制出来还是密文 | 恢复流程找不回上次那个浏览器(Chromium 写的 `DevToolsActivePort` 被「转发启动」的进程删了)⇒ 已在 2026-10-27 修掉,见本节与 ADR-0022 |
| 「开始输入」之后字没出来 | 焦点不在目标软件上(点按钮那一刻焦点在**我们自己的窗口**里)⇒ 按提示等 3 秒把光标移过去 |

### 开发者:相关门禁

- `node --test tools/verify/verify-cdp-copy-repair.cjs` —— **整条链路**端到端
  (起浏览器 → 注入 → 真字形识别 → 下发 → 合成 Ctrl+C → 剪贴板是明文)。
- `node --test tools/verify/verify-page-guard.cjs` —— 页面守卫本身的回归。
- `node --test tools/verify/verify-frame-bridge.cjs` —— 同源 iframe 的帧桥回归
  (站点换掉嵌套 iframe 之后,映射还能不能送到新那层)。
- `node --test tools/verify/verify-glyph-grid.cjs` —— 盯**渲染栅格 == 参考库栅格**
  (不等 ⇒ 位图错位 ⇒ 最近邻全是噪声 ⇒ 永远不还原)。
- `node tools/verify/verify-package-win.cjs` —— 盯**打包产物**里 runtime 依赖齐不齐
  (`vendor/` 下的页面守卫、帧桥、共享核心、字体解析器、参考字形库)。

## 浏览器每隔一会儿自己弹出一个空白标签页(2026-10-27 修掉的真实故障)

**症状**:软件自己开的那个 Edge,过一会儿就**自己弹出一个新的空白标签页**,再过一会儿又弹一个;
界面上「浏览器复制修复」那栏可能从「已接管」掉回「已开启」或者报错;
**网页上复制出来还是密文**。

**原因**(根因见 ADR-0022):CDP 连接断了之后,恢复流程只认 Chromium 自己写的
`DevToolsActivePort` 文件;而**同 profile 的第二个浏览器是「转发启动」**(Chromium 单例)
—— 它退出时会把那个文件**删掉** ⇒ 永远找不回上次那个浏览器
⇒ 每约 29 秒重开一个(还多开一个空白标签页),而且**再也连不回去**
⇒ 新标签页没有页面守卫 ⇒ 复制必然是密文。

**怎么确认**(三步,不是猜):

1. 看产品日志:「浏览器已就绪」只出现**一次**,之后一直是「启动 Edge」;
2. 看 profile 目录里**有没有** `DevToolsActivePort` 文件 —— 故障时它**不在了**;
3. 那个浏览器其实**还活着**:

   ```powershell
   Get-CimInstance Win32_Process -Filter "Name='msedge.exe'" |
     Where-Object { $_.CommandLine -like '*browser-profile*' -and $_.CommandLine -notmatch '--type=' } |
     Select-Object ProcessId, CommandLine
   ```

   (命令行里那个 `--remote-debugging-port=` 就是它真正的调试端口。)

**已修**(2026-10-27):恢复时按三条候选找(自己记的端口 → `DevToolsActivePort` → 扫进程命令行),
三条都试过才允许起新的;起不来自己的端口就改连已经在跑的那个;

## 浏览器一个接一个自己弹出来 / 起来的那几个「根本就不能用」(2026-10-27 修掉的真实故障)

**用户当时看到的原话**:
「只要我打开了，他就反反复复拉起浏览器，而且拉起浏览器一直都是失败，根本就没有一个窗口，起来的浏览器根本就不能用」。

### 怎么判断是哪一类

| 你看到的 | 多半是 |
| --- | --- |
| 窗口**一个接一个**弹出来,每次都是**新的空白窗口** | 「用户关掉了窗口,软件又给弹一个」—— 2026-10-27 之前的老行为 |
| 窗口弹出来但**里面是空的/白的**,点不动 | 页面被守卫冻住了 / 那个标签页的映射没到位 |
| **一个窗口都没有**,但任务栏有图标 | Edge 起了但窗口没显示(虚拟桌面/被别的窗口盖住) |
| 浏览器**一个都没起来** | Edge 路径不对,或调试端口起不来 ⇒ 看下面的日志 |

### 日志在哪

- **浏览器自己的输出**(这才是关键 —— 2026-10-27 之前它被丢掉了):
  - Electron: `%APPDATA%\xyw\browser-profile\browser-stderr.log`
  - Tauri: `%APPDATA%\com.gojocloud.campus-network-connector.tauri\browser-profile\browser-stderr.log`
- **我们自己记的调试端口**:
  - Electron: `%APPDATA%\xyw\browser-profile\simuinput-cdp-port.txt`
  - Tauri: `%APPDATA%\com.gojocloud.campus-network-connector.tauri\browser-profile\simuinput-cdp-port.txt`
- **App 自己的日志**:Electron 看 stdout(开发模式下从终端启动就能看到);
  Tauri 看 `diag.json`(`%APPDATA%\com.gojocloud.campus-network-connector.tauri\diag.json`)。

### 现在是什么行为(2026-10-27 修完之后)

- **你自己关掉那个 Edge 窗口** ⇒ 软件**不会**再自动弹一个;
  界面上的「浏览器复制修复」那一栏会出现
  「浏览器已关闭 —— 本软件不会自动再弹一个」+ 一个 **「重新打开浏览器」** 按钮。
- **浏览器崩了 / 被强杀** ⇒ 仍然**自动恢复**(退出码非 0 ⇒ 不是「你关的」)。
- **连着 3 次起不来** ⇒ 软件**停下来**,并把原因报在界面上(不再无限重试)。
- 界面上**只起一个**浏览器:并发调用也会被「单飞锁」合成一次。

## 分不清自己测的是 Electron 版还是 Tauri 版 / 窗口标题显示「模拟输入」(2026-10-27 修掉的真实故障)

**用户当时看到的原话**:
「Electron版本和那个版本，你根本就没有区分，让我测试」。

### 怎么判断是不是这个问题

| 你看到的 | 说明 |
| --- | --- |
| 界面左上角有「Electron 版」/「Tauri 版」小字,但**任务栏悬停提示 / Alt+Tab 里两个都叫「模拟输入」** | 窗口标题被前端页面的 `<title>` 顶掉了(2026-10-27 之前) |
| 托盘提示也显示「模拟输入」 | 托盘提示没设对 |
| 左上角**根本没有**小字 | 版本徽标没渲染出来(前端没更新) |

### 根因(为什么「源码里写了标题」不等于「窗口上真是那样」)

- **Electron**:默认行为是「**页面标题一变,窗口标题跟着变**」
  (事件 `page-title-updated` 默认就会改标题)⇒ `main.js` 里写的 `title` 被顶掉了。
- **Tauri v2(Windows)**:不是同一个原因 —— 那边是**平台覆盖配置**
  `tauri.windows.conf.json` 把窗口配置整个替换了
  (详见 Tauri 仓 ADR-0035 第六节)。

两个版本的前端 `index.html` 里当时都写着 `<title>模拟输入</title>` ⇒ 两个窗口标题一模一样。

### 现在是什么行为(2026-10-27 修完之后)

- 窗口标题 = **模拟输入（Electron 版）** / **模拟输入（Tauri 版）**
  (任务栏悬停提示、Alt+Tab 里都能看出来);
- 托盘悬停提示同理;
- 界面左上角有常驻徽标;
- 安装名 / 开始菜单名:「模拟输入-Electron」/「模拟输入-Tauri」。

# 字体映射技术说明

本文记录 copy-repair 如何把"网页里被字体混淆的文字"还原成用户看到的文字，
以及每个关键结论背后的实测数据（数据全部来自本仓库 `tools/` 下的实验脚本，可复现）。

> ⚠️ **本文第 2 节描述的"页面渲染位图 → 回传给 App 比对"方案,在真实站点上已被证伪**
> (canvas 与参考库的栅格化器不同,「专」会被判成「令」)。
> **当前生效的方案是「解析字体文件 + 与参考库同一套栅格化器」**,
> 见 [`字体混淆还原-字体文件解析方案.md`](./字体混淆还原-字体文件解析方案.md)。
> 本文其余部分(问题定义、归一化、判据、复制提交机制)仍然有效。

---

## 1. 问题定义

网页可以给一段 DOM 文本挂上一个自定义字体，让**底层字符**与**可见字形**不一致：

| 层 | 内容 |
| --- | --- |
| DOM 文本 | `天地玄黄宇宙洪荒日月盈昃` |
| 字体渲染出来 | `人工智能正在改变世界科技` |
| 浏览器复制得到 | `天地玄黄宇宙洪荒日月盈昃`（底层字符，用户看到的是另一串字） |

要修复，就必须回答一个问题：**这个字形到底是哪个汉字？**

关键前提（也是最容易踩的坑）：

> 字体的 `cmap` 只告诉你"码位 → 字形编号"，**不告诉你这个字形长什么样**。
> 混淆字体里 `天` 的字形轮廓其实是 `人` 的轮廓。直接读 cmap 一定会错。

---

## 2. 采用的方案：不解析字体，直接问浏览器

传统做法是下载字体文件、解析 `cmap`/`glyf`/`CFF `、把字形轮廓与参考字体做形状匹配。
这条路要处理 WOFF/WOFF2 解压、CFF Type2 字符集解释器、GSUB 上下文替换……复杂度很高。

copy-repair 换了个思路：**用浏览器自己的渲染器把字画出来**。

1. 拿到该文本节点的 computed `font-family / font-weight / font-style`（称为"字体作用域"）。
2. 在离屏 canvas 上用这个字体渲染该字符，取 alpha 通道 → 32×32 归一化覆盖度位图。
3. 与本地参考字形库做最近邻匹配，得到"这个字形看起来像哪个字"。
4. 命中且置信度足够时，把底层字符替换成匹配到的可见字符。

好处：

- 不下载、不解析任何字体文件 → 不受 CORS、WOFF2 解压、CFF 解释器限制
- 渲染结果就是浏览器实际显示的样子 → 自动处理可变字体、`unicode-range`、CSS 合成
- 同一份代码在 Chromium 与 Safari 都能跑

代价：

- 依赖浏览器能正确加载并渲染该字体（页面本身依赖它，所以通常成立）
- 单字符渲染无法表达"同一字符在不同上下文里字形不同"的极端情况（见"已知限制"）

## 3. 归一化：两边必须用同一把尺子

参考字形库和目标字体的位图必须在同一坐标系下比较，否则抗锯齿差异会被放大成系统性偏差。

采用的归一化（与字体自身的 ascent/descent 指标无关）：

```
em 尺寸 = 1.0，基线在 y = 0（屏幕坐标，y 向下为正）
窗口：x ∈ [0, 1] em，y ∈ [-0.85, 0.15] em
```

- 参考库：Node 端用 opentype.js 取轮廓 → 自研扫描线栅格化器（4× 垂直超采样 + 水平分数覆盖）→ 3×3 模糊 → 4bit 量化
- 运行时：canvas 以 4× 尺寸渲染 → 面积平均降采样到 32×32 → 3×3 模糊 → 4bit 量化

> **踩过的坑**：最初参考库存的是"未模糊"位图，运行时查的是"已模糊"位图，
> 两边尺度不一致，跨风格准确率被拖低 4 个百分点。统一成"双方都模糊"后立刻回到 93.9%。

另外，运行时渲染位图时，同时用一个**不存在的字体族**渲染一份"对照图"；
若两者一致，说明该字符没有命中目标字体（落到了回退字体），该字符不参与映射。

## 4. 判据：怎么区分"混淆字体"和"正常但风格不同的字体"

这是整套方案最容易出错的地方。三个量：

| 量 | 含义 |
| --- | --- |
| `best` | 参考库里与目标位图最近的字符 |
| `score` | 与 `best` 的相似度（0..1） |
| `margin` | 与次近邻的差距（0..1），置信度 |
| `selfDistance` | 与"该字符自身参考字形"的距离（0..1） |

直觉判据是 `selfDistance` 大 ⇒ 字体画的不是这个字。但实测发现**这条路不可靠**：
`天` 与 `人` 在 32×32 下本身就很像（库内距离 0.168），
混淆字体里 `天` 的 `selfDistance` 只有 0.171 —— 和正常字体的噪声区完全重叠。

**实测标定**（`tools/proto-policy.mjs`，5 套字体 × 238 字符）：

| 字体 | 最近邻≠自身的比例 | 平均 selfDistance | 误判字符的 margin |
| --- | --- | --- | --- |
| 混淆（同风格，Noto Sans SC 轮廓） | 100%（针对字体内字符） | 0.185 | — |
| 混淆（跨风格，Noto Serif SC 轮廓） | 100%（针对字体内字符） | 0.177 | — |
| 正常（与参考库同款 Noto） | 0% | 0.024 | — |
| 正常（衬线 Noto Serif） | 8.0% | 0.107 | ≤ 0.022 |
| 正常（macOS 系统黑体 PingFang） | 5.9% | 0.086 | ≤ 0.022 |

关键结论：

1. **正常字体的误判，最近邻与次近邻的 margin 极小（≤ 0.022）**，而混淆字体的 margin 普遍更大
   → `margin` 是最有效的置信度闸门
2. 正常字体的 `selfDistance` 最大 0.171，混淆字体最小 0.165 → 单看它几乎不可分，但与 margin 叠加后可以分开
3. 正常字体的误判率是**逐字符**的（6~8%），但**逐作用域**看就极低
   → 用"作用域多数投票"把逐字符噪声挡在外面

### 最终判定规则

**逐字符**（`isConfidentSubstitution`），四条同时成立才允许替换：

```
best ≠ 自身
∧ score ≥ 0.8
∧ margin ≥ 0.01
∧ selfDistance ≥ 0.15
```

**逐作用域**（`decideScope`）：采样最多 24 个字符，
"满足上述替换条件"的比例 ≥ 0.6 → 判定该作用域为混淆字体。

实测效果：

| 场景 | 结果 |
| --- | --- |
| 混淆字体（同风格） | 100% 字符被正确还原 |
| 混淆字体（跨风格） | 约 90% 字符被正确还原，其余保持原字符（不伪造） |
| 正常字体（衬线 / 系统黑体） | 作用域判为"非混淆"，一个字都不动 |
| 正常字体（与参考库同款） | 作用域判为"非混淆"，一个字都不动 |

## 5. 还原准确率实测

`tools/proto-accuracy.mjs`（132 字 × 5 套字体）：

```
=== 混淆(同风格) ===
还原正确        : 132 (100.0%)
平均相似度      : 0.9769
平均次优差距    : 0.0932

=== 混淆(跨风格) ===
还原正确        : 124 (93.9%)     ← 未经置信度门限的裸 top-1
  margin>=0.010  接受 114  精度 99.1%  覆盖率 86.4%
  margin>=0.020  接受  96  精度 100.0% 覆盖率 72.7%
```

即：**加上置信度门限后，跨风格也能做到 100% 精度**，代价是只覆盖约 73~86% 的字符。

三种度量的对比（`tools/proto-metrics.mjs`）：

| 度量 | 跨风格裸 top-1 | margin≥0.02 精度 | margin≥0.02 覆盖率 |
| --- | --- | --- | --- |
| **L1（覆盖度平均绝对差）** | **93.9%** | **100%** | **72.7%** |
| IoU（二值交并比） | 81.1% | 91.7% | 81.8% |
| HOG（梯度方向直方图） | 84.1% | 95.9% | 74.2% |

→ 选定 L1。IoU 对笔画粗细过于敏感，HOG 丢失了 CJK 细笔画信息。

栅格分辨率对比：32×32 与 48×48 在相同 margin 门限下精度几乎一致，
32×32 的库体积小一半（4.15MB → 打包后 gzip 1.99MB），故选 32×32。

## 6. 复制提交机制（Chromium 实测，最容易踩坑的一环）

Chromium 对 copy 事件的提交规则：

| 情况 | 系统剪贴板内容 |
| --- | --- |
| `clipboardData.setData(...)`，**不**调 `preventDefault()` | **原始选区文本**（事件里的改写被丢弃） |
| `clipboardData.setData(...)` + `preventDefault()` | **事件里的 clipboardData**（改写生效） |
| 页面只调 `preventDefault()` | 不写入，剪贴板保持原样 |

实验记录（`tools/proto-clipboard-commit.mjs`，有头 Chrome + `osascript` 读剪贴板）：

```
1) Cmd+C 无改写          => "SENTINEL"    （说明 CDP 合成按键不触发 macOS 原生复制）
2) Cmd+C + setData       => "SENTINEL"
3) Cmd+C + 异步写入      => "SENTINEL"
   setData + preventDefault => "MODIFIED-WITH-PD"   ✅
```

推论：

1. **扩展在写入修复文本后必须调用 `preventDefault()`**，否则改写会被浏览器丢弃。
   这与"普通网页不得受影响"并不冲突：只有在我们**确实产出��验证过的替换文本**时才调用。
2. macOS 的 Cmd+C 是**原生菜单动作**，CDP 合成的按键不会触发复制。
   自动化验证改用 CDP 的编辑命令通道 `Input.dispatchKeyEvent{commands:['copy']}`，
   它走浏览器真实的复制命令路径。
3. headless Chrome 同样不提交 copy 事件里的 clipboardData 改写，
   因此**"复制结果是否正确"必须在有头模式下核对系统剪贴板**。

### 防篡改护栏（主世界 document_start 注入）

页面脚本与扩展注入脚本在同一个 JS 世界，页面可以给 copy 事件写上自己的 clipboardData。
护栏在 document_start 打两个补丁：

- `DataTransfer.prototype.setData/clearData`：复制事件派发期间，拦截页面对 `text/plain` 的覆盖
- `Event.prototype.preventDefault`：阻止页面取消本次复制

护栏有两种模式：

| 模式 | 触发条件 | 行为 |
| --- | --- | --- |
| `repair` | 我们有已验证的替换文本 | 全面拦截页面的 setData 与 preventDefault |
| `observe` | 我们没有替换文本 | 仅当页面"既改写 text/plain 又 preventDefault"时，拦下它的 preventDefault |

`observe` 模式的意义：Chromium 在**没有** preventDefault 时会忽略事件里的改写、
直接提交原始选区 —— 所以只要阻止页面的 preventDefault，浏览器就会把用户看到的文字交出去，
不需要我们再写一次剪贴板。

> 已知副作用：会"改写 text/plain 的复制型网站"（例如某些"复制为 Markdown"站点）
> 被还原为可见文本。这是任务书第二级要求（识别并覆盖篡改）的直接后果，
> 计划在第二阶段提供按站点豁免的开关。

## 7. 字体作用域与缓存失效

映射必须按"作用域"缓存：同一个字符在不同 font-family / weight / style 下可能是不同字形。

作用域键 = `style | weight | family`（family 列表归一化：去空白、去引号、保留顺序）。

**字体变更检测**（测试 D 验证）：

- 每次选区分析前先作废渲染缓存，否则会拿旧位图去比对
- 作用域记录一个字体指纹（探针字符渲染结果的哈希）
- 每个已映射字符同时缓存它当时的渲染位图；下次渲染结果不一致 ⇒ 该字符的映射作废重算

## 8. 同步复制链路

复制事件必须**同步**完成，不能在里面等异步字体解析。做法：

```
选中文字 ──► selectionchange（防抖 120ms）
                 └─► 渲染选中字符 → 请求后台匹配 → 缓存映射
                                          │
用户按 Cmd+C ──► copy 事件（同步）
                 └─► 查缓存 → 直接拼出修复文本 → clipboardData.setData + preventDefault
```

页面加载后、用户尚未选中时不做任何字体分析；
选中后提前算好，复制时只做查表与字符串拼接（实测单次修复耗时在毫秒级）。

后台加载的是随扩展打包的参考字形库（gzip 后 1.99MB），**不发起任何网络请求**。

## 9. 参考字形库

- 参考字体：Noto Sans SC Regular（SIL OFL 授权，可随扩展分发）
- 字符集：ASCII + 拉丁补充 + 通用标点 + CJK 标点 + 全角符号 + **GB2312 全部 6763 汉字** = 7949 个字符
- 格式：自研二进制 `CRDB v1`（4bit 量化 + 8×8 粗筛索引 + 32×32 精细栅格）
- 体积：4.15MB（原始）→ 1.99MB（gzip，随扩展打包）

粗筛 + 精筛两段式检索：先用 8×8 粗栅格筛出 256 个候选，再做 32×32 精细比较。
（候选数从 64 提到 256 是必要的：64 会把正确答案筛掉，跨风格准确率损失约 4 个百分点。）

# 字体混淆还原:字体文件解析方案(真实页面实测)

> 本文记录一次**真实目标页**(学习通 mooc1.chaoxing.com)上的完整取证与方案定型过程。
> 结论先行:**页面 canvas 渲染位图这条路走不通,必须解析字体文件。**

---

## 1. 真实目标页的结构

| 项 | 实测结果 |
| --- | --- |
| 顶层 | `mooc1.chaoxing.com/mycourse/studentstudy?...` |
| 题目所在位置 | **第 4 层嵌套 iframe**(`top/0/0/0`,`mooc-ans/work/doHomeWorkNew`) |
| 同源性 | 全部同源 → 可递归注入 |
| 加密字体 | `font-cxsecret`(定义在**内联 `<style>`** 里,`data:` base64 内嵌 TTF,10.4KB) |
| DOM 原文 | 「【单选题】**垕垖**中国专利法实**垔**新型和**垘**观设计**垙**予的期**垗垚** …」 |
| 可见文字 | 「【单选题】**目前**中国专利法实**用**新型和**外**观设计**授**予的期**限为** …」 |

DOM 里只有**一部分**字符被加密(其余是明文),所以不能按整段文本猜,只能逐字映射。

## 2. 三次关键判断(都有实测数据)

### 2.1 密文字形 ≠ 明文字形(逐位比较失败)

用同一个字体渲染「密文字」与「明文字」,位图 L1 距离不为 0:

| 密文 | 与「根」的 L1 | 与「目」的 L1 | 结论 |
| --- | --- | --- | --- |
| 垕(U+5795) | 不等于 | 不等于 | 密文字形是**重绘**的,不是明文字形的副本 |

→ **精确位图查表(hash)必然 0 命中**。这条路(页面侧自建字形表)被实测否决。

### 2.2 密文字体只有 28 个字形

解析 `font-cxsecret`(opentype.js):字形数 **28**,不同轮廓 **27**,cmap 里只有 27 个码位
(U+5794…U+580A),**不包含任何常用汉字**。

→ 这是**专用密文字体**:每个密文码位对应一个手绘重绘的明文字形。
   也说明"页面侧用同一个字体渲染常用字建表"必然失败:那个字体根本没有常用字。

### 2.3 参考字体必须是 Noto Sans SC

用同一套栅格化器(48×48、4bit 量化)比对 27 个密文字形:

| 参考字体 | 平均最优距离 | 平均 margin | 判定质量 |
| --- | --- | --- | --- |
| Noto Sans SC | **0.031** | **0.116** | 27/27 全中 |
| Noto Serif SC | 0.118 | 0.045 | 4 个错(处/眼/诀/－) |

→ 站点的字形来源是**黑体系**(宋体/雅黑),Noto Sans SC 与它最接近。

ASCII art 直接比对也印证了这一点:密文「垛」的字形(两横 + 竖 + 乚)与「专」**完全一致**,
与「家」明显不同 —— 也就是说**页面上用户看到的就是「专」**,我们要还原的正是"可见文字",
而不是站点原文。

## 3. 为什么必须解析字体文件(而不是页面渲染位图)

| 方案 | 相似度 / 距离 | 结果 |
| --- | --- | --- |
| 页面 canvas 渲染 → 回传位图 → 主进程比对 | 相似度 0.87~0.97,margin 低至 **0.005** | 「专」被判成「令」;「国」判不出 |
| 主进程解析字体 → 同一套栅格化器 → 比对 | 距离 **0.001~0.043**,margin **0.03~0.19** | **27/27 全中** |

根因:canvas 的字形栅格化与参考库的栅格化器**不是同一套**(抗锯齿、合成方式、hinting 不同),
距离一拉大,最近邻就分不出「专 / 令」「国 / 固」。

栅格尺寸也有讲究:

| 栅格 | 参考库字数 | 27 个密文字的判定 |
| --- | --- | --- |
| 32×32 | 21517(GBK) | 26/27(「国」margin 仅 0.0045,判不出) |
| 48×48 | 7949(GB2312) | **27/27** |

最终采用 **48×48 + GB2312** 参考库(9.4MB,只存在于本机)。

## 4. 最终架构

```
网页内(page-guard.js)
├─ selectionchange
│   ├─ 按字体作用域分组(同一次选区可能混着普通字体与密文字体)
│   ├─ 收集该作用域的「字符集合」
│   └─ 解析该作用域的 @font-face 字体文件(data: base64 或 URL)→ 一并上报
│       ↑ 只在**同源可读**的样式表/内联 style 里找;跨源样式表读不到 → 该作用域不动
└─ copy 捕获(window 捕获阶段)
    ├─ 查映射表(按字符所属作用域)
    ├─ 有映射 → setData + preventDefault(浏览器提交我们写的内容)
    └─ 无映射 → **什么都不做**(保留用户原始复制,绝不取消默认动作后写空)

主进程(engine.js)
├─ 拿到字体字节 → opentype.js 解析 → 取每个码位的字形轮廓
├─ 用 core 的栅格化器转成 48×48 覆盖度位图(与参考库**同一套**、同 4bit 量化)
├─ 与 Noto Sans SC 参考库做最近邻匹配 → 得到「这个码位画的是哪个字」
├─ 置信度闸门:相似度 ≥0.8、margin ≥0.01、自身距离 ≥0.15
│   (margin 接近时用「常用字优先」打破平局,例如「一」vs 全角连字符)
└─ 字体按内容 sha1 缓存,同一字体只解析一次
```

### 判定闸门的含义

- **自身距离**(字形 ↔ 同码位在参考库里的字形)≥ 0.15:证明这个字体**确实把该码位画成了别的字**;
  正常字体的同一码位距离只有 0.02~0.05,会被这条挡掉 → 普通字体一个字都不动。
- **margin**(最优 ↔ 次优)太小 = 分不清 → 不改,保留原始复制。
- 三条任一不满足 → 该字保持原样(宁可留一个错字,也不写错字)。

## 6. 这条路线的已知限制

| 限制 | 说明 |
| --- | --- |
| **跨源 iframe 无解** | 注入跨源 iframe 抛 SecurityError,copy 事件也不跨 frame 冒泡(实测)。技术限制,不做掩盖。 |
| **@font-face 在跨源样式表里就读不到** | 页面拿不到字体文件 → 该作用域不做任何替换(安全降级)。可由主进程按 Resource Timing 里的 URL 兜底下载,本版未做。 |
| **参考库覆盖 GB2312(7949 字)** | 明文里出现更生僻的字时匹配不到 → 该字保持密文原样,其余照常还原。 |
| **不是所有混淆字体都是"专用密文字体"** | 若站点用"把明文字形搬到密文码位"的字体(字形完全相同),本方案同样成立(距离≈0);若字形被大幅重绘,相似度会下降,置信度闸门会拒绝替换。 |
| **48×48 参考库 9.4MB** | 只落在本机磁盘,不进网页、不上传。 |

## 7. 后续加固(2026-10-20 晚):自动选参考库 + 保守闸门

### 7.1 为什么要"自动选参考库"

实测:同一个密文字体,换参考字体会直接改变结论。

| 参考库 | 平均距离 | 平均 margin | 结果 |
| --- | --- | --- | --- |
| Noto Sans SC 48×48 | 0.031 | 0.116 | 27/27 全中 |
| Noto Serif SC 48×48 | 0.118 | 0.045 | 错 4 个 |

**距离小 = 底稿字型与参考库越接近。** 那怎么知道该用哪套?

答案藏在字体的 `name` 表里 —— 它记着**底稿字族**:

```
fontFamily: Source Han Sans CN Normal   ← 底稿
```

思源黑体(Source Han Sans CN)与 Noto Sans SC 是**同一个字型**(Adobe/Google 联合出品),
所以拿 Noto Sans SC 当参考天然最接近。引擎现在会:

1. 读 `name` 表 → 归一化字族名
2. 按关键字(serif/song/sans/hei/pingfang…)把候选参考库排序
3. 逐个试,取**平均距离最小**的那个;底稿命中的库如果拟合良好(平均距离 ≤0.12)就不再多试
4. 拟合质量写进日志,便于事后核对

### 7.2 自动选库的验证(合成字体,宋体底稿)

用 `tools/make-obfuscated-font.mjs` 从 Noto Serif SC 造一个"明文字形搬到密文码位"的字体
(132 个字),`name` 表写 `Noto Serif SC`:

| 运行方式 | 正确 | 不确定 | 平均距离 |
| --- | --- | --- | --- |
| **自动选库** | **131/132** | 0 | 0.0897 |
| 强制黑体库 | 100/132 | 26 | 0.1447 |
| 强制宋体库 | 131/132 | 0 | 0.0897 |

→ 自动选库与最优人工选择一致;选错库会掉 24 个字、且 26 个字进入"不确定"被保守跳过。

### 7.3 保守闸门:宁可留错字,不可写错字

- margin 不足 → 该字**不替换**,记入 `uncertain` 供诊断
- 相似度不足 / 自身距离不足 → 同样不替换
- 合成字体那 1 个未解出的字(「天」→应为「人」)就是被闸门挡下的 —— 结果是**131 个全对、0 个错**

### 7.4 字体内容指纹(防止站点换字体后映射残留)

作用域 key 现在带**字体内容指纹**(`fontStyle|fontWeight|fontFamily#<内容哈希>`):
站点换字体(族名不变、字形全变)时 → 新作用域 → 重新映射,
不会拿旧字体的映射去套新字体。

### 7.5 最终形态:只带一套黑体参考库

产品只服务目标站点,其加密字体底稿就是**思源黑体**(name 表实测 `Source Han Sans CN Normal`),
与 **Noto Sans SC 是同一字型**,所以:

- 参考库只保留 **Noto Sans SC 48×48**(9MB),宋体那套已删除
- 引擎仍读 `name` 表把底稿字族记进日志,便于日后判断是否要换库
- 32×32 那套(旧默认)也一并删除 —— 48×48 才分得清「国/固」

体积账:vendor 目录从 **25.9MB**(32格11.5 + 48格9 + 宋体9 + 其它)降到 **9.8MB**。

### 7.6 打包产物自检

```
/vendor            6 个文件:page-guard.js / frame-bridge.js / copy-repair-core.cjs
                             common-charset.js / opentype.js / glyph-db-48.crdb.gz
/safari-repair     bridge / engine / coordinator / index + test(回归用)
/mac-coregraphics  原生模块(macOS 专用)
```

跨平台注意:原生模块只存在于 macOS,`main.js` 已改为**按平台加载 + 统一兜底**,
Windows 上不会因 `require` 失败而崩溃;Safari 复制修复开关在非 macOS 平台自动隐藏
(IPC `safariRepair:getStatus` 返回 `supported: false`)。

## 8. 真实缺陷:只还原了第 1 题(2026-10-20 晚)

### 8.1 现象

页面上有 5 道题,全部用同一个加密字体。复制整块内容时:

- 第 1 题正常(「目前中国专利法实用新型和外观设计授予的期限为()」)
- 第 2~5 题仍是密文

### 8.2 根因

**映射是按"选区"建的,不是按"字体"建的。**

引擎原先只还原"采集那一刻选区里出现过的字":

```js
for (const char of limited) {          // limited = 选区里的字
  const info = entries.get(char.codePointAt(0));
  if (!info) continue;
  mapping[char] = ...;                 // 只写选区里的那些字
}
```

于是:先选了第 1 题 → 映射里只有 7 个密文字;后来把选区扩大到 5 题,
新出现的密文字**不在映射里** → 复制出来还是密文。

实测数据(第 4 层 frame):

```
作用域 400 | font-cxsecret | 字符数=671 元素=58   ← 整页 5 题都在这个作用域
映射只有 7 个 (垕垖垔垘垙垗)                        ← 只有第 1 题的密文字
pending 102 字 font-cxsecret 字体=data:13824         ← 采集到了，但没被消费
```

### 8.3 修法

**映射按字体建**:字体里每个码位的对照关系已经算好了,整份下发即可,
任意选区都覆盖得到。

```js
for (const [cp, info] of entries) {    // 整份字体
  ...mapping[String.fromCodePoint(cp)] = String.fromCodePoint(info.plain);
}
```

安全性不变:非密文字的码位会被"自身距离"闸门挡掉(它的字形就是它自己)。

### 8.4 回归测试(有牙齿)

`node safari-repair/test/loop.cjs` 增加第二阶段:

1. 阶段1:选 `#target` → 采集 → 复制 → 校验
2. **停掉协调器定时器** → 选 `#target2`(另一段密文) → **不重新采集** → 直接复制 → 校验

停定时器是关键:否则协调器会在选区变化后偷偷跑一轮,重新采集+下发映射,把回归点盖掉。

实测:

| 引擎行为 | 阶段2 |
| --- | --- |
| 修复前(按选区建映射) | ✖ 失败(新密文字没被还原) |
| 修复后(按字体建映射) | ✔ 通过 |

### 8.5 真实页复验

程序化选中全部 5 题(291 字符)后做页面内改写:

```
changed=37   cipherKinds=27   cipherLeft=0
【单选题】目前中国专利法实用新型和外观设计授予的期限为()。
【单选题】目前中国专利法发明专利授予的期限为()。
【多选题】以下选项中,专利权的特点有()。
【判断题】根据专利的推定有效性,一件专利申请在公众对其有异议时,就应当进来司法救济程序解决争议。()
【判断题】专利知识仅仅在所在申请国具有法律效力。()
```

`cipherLeft=0` → 输出里再没有任何密文码位。

> 顺带一提:第 5 题原文是「专利**知识**」(题库笔误,应为"专利权")。
> 字形比对给出「知」,与页面上画出来的字形一致 —— 我们还原的是**可见文字**,这正是需求。

## 9. 规模:字体里"所有可能用到的字"必须全部映射

### 9.1 需求

不只还原当前这一份题:站点换一批题,会用到**完全不同的一批**密文字,而且可能多得多。
所以要求是:**字体里所有可能用到的字,全部都要映射到**,而不是"这次选区里出现过的字"。

### 9.2 原来的性能撑不住

用 core 的 `GlyphDb.lookup` 逐字查全库(7949 条),实测 **5.36ms/字**:

| 字体规模 | 映射耗时 | 后果 |
| --- | --- | --- |
| 27 字(真实站点当前这批题) | 146ms | 无感 |
| 1000 字 | **5.4 秒** | 用户来不及等 → 复制出来还是密文 |
| 3000 字 | 16 秒 | 完全不可用 |

热点拆解(200 次查询):粗距离循环 1.8ms/字、512 次精筛 ~3.4ms/字、全量排序 0.2ms/字。

### 9.3 快速匹配器(`safari-repair/fast-matcher.js`)

1. **精确哈希快路径**:密文字体通常是把明文字形**原样搬到**密文码位
   (这类字体的字形与参考字形逐位相同,距离 0.0000)。
   预建「量化位图哈希 → 码位」表,命中即 O(1)。
2. **更快的最近邻**(字形被重绘、哈希命中不了时走这条):
   - 粗距离:预展开参考库的 nibble 数组,省掉每次解包与查表
   - 精筛:**部分选择**代替全量排序(只留前 256 个候选)
   - 仍然用同一套栅格化器与同一个参考库 → 判定口径不变

实测(与旧实现逐字对比:**27/27 判定完全一致**):

| 字体规模 | 旧实现 | 新实现 | 覆盖率 | 正确率 |
| --- | --- | --- | --- | --- |
| 27 字(真实站点,重绘字形) | 146ms | **120ms** | 27/27 | 27/27 |
| 132 字(仓库测试字体) | ~700ms | **49ms** | 132/132 | 132/132 |
| 1000 字 | 5356ms | **169ms** | 1000/1000 | 1000/1000 |
| 3000 字 | ~16s | **435ms** | 3000/3000 | 3000/3000 |

### 9.4 规模回归测试

```bash
node safari-repair/test/stress-font.cjs                    # 仓库自带 132 字字体
node safari-repair/test/stress-font.cjs --font <参考字体> --n 3000   # 合成 3000 字字体
```

断言三条:**映射条数 = 码位总数(全覆盖)、判定正确率 = 100%、耗时在预算内**。

> 这是对"所有可能用到的字都要映射"这条要求的**可执行断言**,
> 以后有人把映射改回"只映射选区里的字",这个测试会直接失败。

### 9.5 顺带修的两个"面向未来"的边界

1. **按字重挑 @font-face**:同一字体族可能有多条 `@font-face`(不同字重各一个文件)。
   原来一律取第一条 → 700 字重的密文字会拿 400 的字形去比,必然判错。
   现在按作用域的 `font-style` / `font-weight` 排序挑
   (完全相同 > 区间包含 > 未声明/normal > 其它),再选可用的 src。
2. **字体缓存有上限**:字体按内容哈希缓存,但原来**无上限**,
   长时间用、题库又多时会累积成几十 MB。现在只保留最近 8 份。

### 9.6 清理掉的遗留

| 东西 | 问题 | 处理 |
| --- | --- | --- |
| `safari-repair/vendor/` | 与根 `vendor/` 完全重复 | 删除,lab 脚本改指根目录 |
| `test/cleanup.cjs` | **会关掉用户窗口**(按 "URL 含 127.0.0.1" 关窗) | 改成只列出候选,且只关"单标签本地页";默认不关 |
| `test/fixtures/fonts/obf-same-style-2.ttf` | 无人引用 | 删除 |
| `test/` 目录进安装包 | 回归脚本+测试字体不该装到用户机器 | `package.json` 的 files 加 `!safari-repair/test/**/*` 排除 |

## 10. 真实缺陷:"最新版本完全不能用了"(2026-10-20 深夜)

### 10.1 现象

装上打包版 App 后:复制**完全不被修复**(连之前正常的第 1 题也不行了),
而此前用调试脚本手动注入时是好的。

### 10.2 根因(两处叠加)

实测状态(学习通页,标签 19):

```
top/0/0/0  guard=false  选区=318   ← 题目所在的最深 frame,守卫不见了
```

**① App 只往"前台标签"注入**
`bridge` 的目标固定是 `front tab of front window`。用户切到别的标签时,
学习通页拿不到新的注入;而那一页第 4 层 frame 的守卫又丢了
(iframe 文档被重建/导航,顶层的 MutationObserver 察觉不到跨文档的变化)
→ 复制事件在那个 frame 里派发,**没有任何人拦截** → 复制出原始密文。

**② 映射要等"选中"之后才建**
守卫在选区变化时才上报,App 解析字体、建映射、再下发,要一两轮(约 0.6 秒)。
用户切到标签页后**马上**复制,映射还没到 → 这一次复制不修复。
用户的感觉就是"要等几秒才行",等久了又忘了,于是"完全不能用了"。

### 10.3 修法

**① 预热(prefetch):装好就建映射,不需要选区**

守卫装好后立刻扫一遍本页(实测 **13ms**):
把所有**有 @font-face 规则的字体族**连同字体文件一起上报。
App 侧随即解析字体、建好映射、下发 → **用户什么时候复制都是热的,零等待**。

```ts
// page-guard.ts
function collectPrefetchScopes() {
  // 遍历元素 → 取计算样式 → 按 (style|weight|family) 去重
  // → resolveFontSource() 拿到字体文件 → 上报
}
```

预热比选区上报更严(相似度 ≥0.88):图标字体的"最佳匹配"距离很大,
用严闸门挡掉,避免把图标映射成汉字。

**② 协调器看住标签页**

- 凡是上报过自定义字体的标签,登记进 `watched`
- 每 10 轮(约 3 秒)复查一次这些标签:守卫没了就重注入,映射重新下发
- 标签可能被关掉/换位 → 用 `pollState` 返回的 `location.href` 校验,URL 不符就取消看住

**③ 前台标签每轮都处理**,所以用户切到哪个标签,那��标签马上就有守卫 + 热映射。

### 10.5 真正的元凶:frame-bridge 的"我注入过就不用再注入"

上面两处修完仍然复现。实测状态:

```
top/0/0/0  guard=false  选区=338   ← 题目 frame 又没守卫了
```

看 `frame-bridge` 的旧逻辑:

```ts
if (framesInjected.indexOf(frameWin) >= 0) return;   // ← 只看"注入过没有"
frameWin.eval(guardSource);
```

站点换题/刷新题目区域时会**重建 iframe 的 document**:
**WindowProxy 还是同一个对象,但 document 已经是新的** → 守卫早就没了,
而 bridge 认为"这个 frame 我注入过了,不用管" → **该 frame 永远没有守卫**
→ copy 事件在那个 frame 里派发,没人拦截 → 复制出原始密文。

而且顶层的 MutationObserver **察觉不到跨文档的变化**(它只看顶层 DOM)。

修法两条:

1. `injectInto` 改成看 frame 里**现在**有没有守卫,而不是"注入过没有"
2. 新增 `selfHeal()`:重新扫描 DOM + 给守卫已丢失的 frame 补注入;
   由**顶层**守卫在每次采集时调用(顶层自己通常没有选区,
   所以自愈必须放在 `collectAndStage` 的**任何 early return 之前** —— 我第一版
   放在后面,顶层永远走不到,自愈形同虚设)

实测:手动删掉最深 frame 的守卫 → 一轮调度后 → `restored: true`,
并且新字体的 35 条映射同时到位。

新一套题(专利保护的对象)用的是**另一份加密字体**(36 字形,底稿仍是思源黑体):
引擎 35 个字**全部通过判定**(score 0.91~0.98、margin 0.035~0.18)。

### 10.7 另一个"完全不能用"的原因:关掉 App 窗口 = 功能停摆

用户反馈"最新版本完全不能用了"。查下来是**两个独立原因**同时成立。

**现象证据**:剪贴板内容没变(被用户打字覆盖)、目标 frame `mappings: []`、
pending 一直是 3(上报了没人消费)。系统日志显示:

```
23:02:00  No windows open yet / Restoring windows   ← App 被重新打开
23:02:05  _kLSApplicationWouldBeTerminatedByTALKey=0
23:02:10  _kLSApplicationWouldBeTerminatedByTALKey=1  ← App 退出了
```

**根因**:`main.js` 里

```js
app.on('window-all-closed', () => { app.quit(); });
```

用户随手把 App 窗口关掉 → App 退出 → **常驻的复制修复跟着死** →
复制出来当然是原始密文。而 Dock 图标还在,看起来"App 还在",极具迷惑性。

**修法**(macOS 惯例):

```js
app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});
```

关窗口后 App 继续在后台跑(点 Dock 图标可再开窗口,`activate` 里会重建)。

**配套**:App 重启后"看住的标签"集合会清零 → 之前盯着的学习通页在它再次成为前台标签之前没人管。
所以把看住的标签 **URL 持久化** 到 `settings.json`,启动时按 URL 找回索引并恢复看住
(`restoreWatched`)。

| icomoon(图标) | 3% | ✅ 判为普通字体,不做映射 |

## 11. 真实缺陷:「复制只修好一半」(2026-10-21)

### 11.1 现象

学习通测验页(`mooc1.chaoxing.com`)复制,剪贴板里:

```
【单选题】固定导轨的安装扣最先在()的安装上使用。            ← 修好了
【判断题】一旦有人提出无抲宣告请求,专利局抸者法抶就必曳抷理。  ← 抲抸抶曳抷 仍是密文
```

### 11.2 排查(每一步都有实测,不是一个猜一个猜)

| 假设 | 怎么验 | 结果 |
| --- | --- | --- |
| 映射表里没有这些字 | 导出映射表全表 | ❌ **有**:抲→效、抸→或、抶→院、曳→须、抷→审 |
| 作用域不止一个、查错了表 | 逐 frame 导出作用域 + 映射条数 | ❌ 全页**只有一个** `@font-face`、一个作用域、19 条映射 |
| 字体被换了、指纹变了 | 对比 @font-face 与作用域指纹 | ❌ 指纹稳定(`normal\|400\|font-cxsecret#datalzv4nl`) |
| 判定逻辑写错了 | 逐字复算 `applyMapping` 的查表路径 | ❌ 现在能全部命中(所以逻辑本身没错) |
| **作用域缓存没赶上选区** | 清空采集缓存后立刻复制 | ✅ **命中** |

### 11.3 根因

查表要两样东西:

1. 这个字**画成了哪个字**(码位→明文)—— 主进程下发的映射表,按字体整份下发,不会过时
2. 这个字**属于哪个字体作用域** —— 页面现算

第 2 样以前是**采集缓存**(`state.charScopes`),由 `selectionchange` 和 App 的轮询更新,
**比复制慢一拍**。于是:

- 早先选过的字 → 缓存里有 → 修好了(单选题)
- 刚选到的字 → 缓存里还没有 → 查表落空 → 原样进剪贴板(判断题)

**映射表是全的,但"这个字属于哪个字体"这份缓存没赶上。**

### 11.4 修法(守卫 v5 → v6)

复制时**当场**按当前选区从 DOM 现算"字符 → 作用域":

```ts
function resolveLiveScopes(state) {
  const live = new Map();
  const collected = collectSelection();          // 当前选区的每个 run
  for (const run of collected.runs) {
    const scopeKey = `${run.scope}#${fontFingerprint(resolveFontSource(...))}`;
    for (const ch of run.chars) if (!live.has(ch)) live.set(ch, scopeKey);
  }
  // 解析不出来的回退到采集缓存
  for (const [ch, scope] of Object.entries(state.charScopes)) if (!live.has(ch)) live.set(ch, scope);
  // 回写缓存,让缓存跟着当前选区走
  for (const [ch, scope] of live) state.charScopes[ch] = scope;
  return live;
}
```

要点:

- 作用域 key 公式与采集路径**完全一致**(否则对不上主进程下发的表)
- 作用域 key 里仍含**字体内容指纹** → 站点换字体照样换作用域、重新建映射,没有放松这个保护
- **不能**用"在所有作用域里全局搜这个字"来兜底:明文字「户」恰好是密文映射表的**键**,
  全局搜会把正常字误替换成「上」

### 11.5 验证(红/绿对照)

仓库自带闭环测试(`src/features/safari-repair/test/loop.cjs`)新增阶段3:
选一段**从未采集过的新密文字**,并且**选区与复制在同一次同步执行里完成**(模拟"改完选区马上按 Cmd+C")。

| 守卫 | 剪贴板 | 结论 |
| --- | --- | --- |
| v5(旧) | `闰余成岁律吕调阳云腾致雨露结为霜金生丽水玉出昆冈` | ✖ 原样密文 |
| v6(新) | `推理应用场景需求用户体验设计开发测试部署运维监控` | ✔ 全部还原 |

真实站点(`tools/lab/verify-fastcopy.cjs` 清空采集缓存后复制):19 个密文码位**残留 0**。

### 11.6 顺带修掉的验收脚本坑

`tools/verify/verify-app-e2e.cjs` 原先用 Unicode 区段(U+3400–U+4DBF)猜"密文字",
而真实密文字在 **U+62xx / U+66xx / U+78xx** → 永远判不到 → **假通过**。
现改为按页面里实际下发的映射表判定(表里的键 = 被混淆的码位),并加"明文片段命中"交叉验证。

## 12. 通用性专项:修法必须对"没给过的场景"也成立(2026-10-21)

第 11 章修好了"选区刚换就复制"的竞态。但那版修法有个**偷懒假设**:
查表时,一个字符只对应一个字体作用域(全局"字符 → 作用域"表)。
这个假设在"字符身份唯一"时成立,**在真实页面上不成立**。

### 12.1 问题一:同一个字出现在两个作用域 → 写出错字

混淆字体的**密文码位恰恰是常用字**(天/地/问/水/土…)。
于是同一个字在一次选区里可能出现两次:

| 位置 | DOM 里的字 | 字体 | 屏幕显示 | 正确结果 |
| --- | --- | --- | --- | --- |
| 甲 | 天 | 混淆字体 | 人 | **人** |
| 乙 | 天 | 普通字体 | 天 | **天** |

按字符身份 → 只能记一个作用域 → 另一处被一起改掉。

实测(`src/features/safari-repair/test/generality.cjs` 用例 s2-obf-first,旧实现):

```
期望 = "人天"
实际 = "人人"      ← 普通那处被改成了「人」:错字
```

**修法**:按**出现位置**判定 —— 把选区拆成逐个文本节点的片段,
每段带自己的作用域,逐段查自己的表、逐段替换,再拼回浏览器那份选区文本。

```
片段1「天地玄黄」→ 作用域 A(混淆)→ 查 A 的表
片段2「普通文字」→ 作用域 B(普通)→ 无映射,原样
片段3「宇宙洪荒」→ 作用域 A → 查 A 的表
```

### 12.2 对齐坑:浏览器的选区文本是"渲染后的"

`selection.toString()` 是**渲染后的文本**(空白按 CSS 折叠),
而文本节点原文里带着制表符、缩进换行。直接拿原文去比对必然对不上:

```
容器: BODY  选区长度: 216
段落: #0 <BODY> len=1 idx=-1 "\t"     ← 第一段就断了 → 整页都没还原
```

**修法**:对齐时**只比对非空白字符**,空白一律当分隔符;
输出的骨架仍是浏览器那份 → 换行、缩进都保留。
对不上的部分**原样保留**(宁可留密文,也不猜)。

### 12.3 问题二:参考库缺字 → 写出错字(燚 被写成焱)

参考库原来只含 **GB2312**(7949 字)。库里**缺**某个明文字时,
最近邻会给出"形近但不是它"的字,而且**分数与 margin 都过闸门**:

| 明文字 | 会被认成 | 相似度 | margin | 闸门 |
| --- | --- | --- | --- | --- |
| 燚 | **焱** | 0.812 | 0.074 | 全过 → 写错字 ✗ |
| 垚 | **寺** | 0.841 | 0.020 | 全过 → 写错字 ✗ |
| 鿕 | **鲋** | 0.837 | 0.011 | 全过 → 写错字 ✗ |
| 㶿 | **饽** | 0.895 | 0.029 | 全过 → 写错字 ✗ |

**靠提高阈值挡不住**:真实字体的逐字分数最低只有 **0.8881**
(站点把字形重绘过,与参考字形不是逐位相同),
错配案例是 0.81~0.90 —— **区间重叠,分不开**。

**修法**:参考库换成 **GBK 全集**(21526 字),gzip 分发(24.4MB → 9.7MB)。
换成全集后真答案在库里,最近邻自然就是它;仍认不出的被闸门挡住 → **零错字**。

配套加一道**零风险预筛**:自身距离不够(没被重映射)的码位跳过最近邻。
这与原判定**完全等价**(拟合率本来就要求自身距离达标),只是省掉全库检索。

### 12.4 通用性用例(常驻回归)

`src/features/safari-repair/test/generality.cjs`,7 个用例全是"用户没给过"的场景:

| 用例 | 场景 | 期望 |
| --- | --- | --- |
| s1-plain-first | 普通在前 + 密文在后 | 天人 |
| s2-obf-first | 密文在前 + 普通在后 | 人天 |
| s3-pure-obf | 纯密文 | 人工智能正在改变世界科技 |
| s4-pure-plain | 纯普通文字 | 一个字都不动 |
| s5-mixed | 密文与普通文字混在一段 | 人工智能普通文字正在改变 |
| s6-two-fonts | 同一个字在**两种混淆字体**里画成不同的字 | 人工智能工智能正 |
| 整页一次选中 | 多作用域 + 同字跨作用域同时出现 | 全部正确 |

真实站点:164 字符、27 个密文码位**残留 0**,与"按映射替换后的期望文本"**逐字一致**。

### 12.5 仍然存在的边界(不是"只对某些题成立",而是能力边界)

- 跨源 iframe:注入被同源策略拦,copy 事件也不跨 frame 冒泡 → 无解
- @font-face 在跨源样式表里:页面读不到 → 该作用域不还原
- 明文的字形与参考库里的字**差太远**(站点重绘得很厉害):闸门挡住 → 留密文(不写错字)
